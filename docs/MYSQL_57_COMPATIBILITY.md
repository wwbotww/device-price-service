> 目标实例：公司内网 MySQL 5.7.36
> 目标库：`device_price`
> 当前账号：暂用 root；不得把密码写入 Git、镜像或日志
> 当前状态：阶段 I～L 完成；公司 head 为 `b72c910e4f31`；M 的备份、迁移、采集与本地回归完成，但严格重放发现 6 组 iMac 重复身份，未通过最终验收，待限定修复授权

## 1. 兼容范围

项目最低支持 MySQL 5.7.8，以确保原生 JSON 可用；公司实例为 5.7.36。MySQL 8.x 继续受支持。

连接建立时程序会：

1. 查询并校验服务端版本；
2. 拒绝低于 5.7.8 或无法识别的版本；
3. 执行 `SET SESSION time_zone = '+00:00'`。

数据库约束由 Alembic 迁移安装：MySQL 5.7～8.0.15 使用触发器模式，MySQL 8.0.16+ 使用原生 `CHECK`。普通连接不会安装触发器、修改数据库版本或改变全局配置。

## 2. 数据约束

MySQL 5.7 解析但不执行 `CHECK`。历史迁移 `6f2a91d4c8b7` 会在旧版本上为以下 V1 表建立 `BEFORE INSERT/UPDATE` 触发器；保留这段历史链不代表当前应用继续读写 V1：

- `product`；
- `sales_channel`；
- `crawl_run`；
- `sku`；
- `official_offer`；
- `price_current`；
- `price_history`。

这些历史触发器覆盖状态枚举、CNY/CN/官方直营口径、非负计数、正金额、原价语义和价格历史时间区间。V1 的应用 DTO、校验器和 Repository 已在阶段 L 删除；当前采集只调用 V2 Pydantic、质量门禁和 Repository 事务。

V2 影子迁移 `96524222b3ec` 为 13 张 `v2_` 表补充同类约束，包括 `RETAIL_AVERAGE/WHOLESALE_AVERAGE`、来源日价格、批量证据归属和同日修订身份。完整 V1+V2 head 在 MySQL 5.7 上共有 40 个校验触发器；MySQL 8.0.16+ 使用原生 `CHECK`，不创建这些触发器。

设备阶段 I 追加迁移 `b72c910e4f31`：MySQL 5.7 仅重建 `v2_crawl_record` 和 `v2_price_observation` 的 4 个校验触发器，保留原校验并增加 `PRODUCT/AVAILABILITY_ONLY`；MySQL 8.0.16+ 替换对应的 3 个 CHECK。仍为 23 张业务表、40 个 MySQL 5.7 触发器，不升级数据库版本或改变全局配置。已有新类型事实时，降级在任何 DDL 前拒绝。2026-09-11 已在本地 5.7.36/8.4 完成验证，并在获准备份、恢复验证与迁移演练后增量部署公司库；实现见[阶段 I 报告](V2_PHASE_I_BUILD_REPORT.md)，部署隔离核验见[阶段 M 记录](V2_PHASE_M_ACCEPTANCE_REPORT.md)。

### 2.1 阶段 L 的运行时与迁移边界

- 唯一 V2 运行时及 SQLAlchemy 元数据只包含 13 张 `v2_` 表；五品牌设备与两个政府来源共用采集、校验和持久化链路。
- 从 Alembic base 升级仍由未改写的历史迁移创建 10 张 V1 和 13 张 V2 业务表；保留旧表及数据，不新增删表迁移。阶段 J～L 没有追加迁移，head 仍为 `b72c910e4f31`。
- `migrations/schema_scope.py` 将自动生成迁移的反射范围限定为 `v2_`，防止已退出 ORM 的 V1 表或同库其他非 V2 表被误判为应删除对象。
- `db check` 只要求 13 张 V2 表；`db audit` 只读检查 V2 数据，不依赖或读取 V1 表，`--check-artifacts` 可额外校验本地证据文件。
- `catalog replay --record-id <ID>` 只读原始证据，在原时点重放全部 SKU 或政府文档行，不联网、不新建批次、不写价格。旧政府上下文可在证据完整时从已保存来源 URL、品种 ID 和发布日期确定恢复。

本地 V2-only 验证和完整历史链验证是不同场景：前者证明运行无需 V1 表，后者证明增量部署不影响保留的历史表。不要为了满足“13 张运行表”而在公司库手动删掉另外 10 张历史表。

### 2.2 设备并发写入的事务隔离

阶段 M 的真实首轮并发暴露两处 `REPEATABLE READ` 空范围间隙锁：旧批次查询阻塞其他来源的新批次插入，以及新规格的开放匹配查询阻塞其他来源的匹配插入。修复限于现有调用链：批次启动已由来源/地区命名锁互斥，因此移除旧批次查询冗余的 `FOR UPDATE`；仅设备单产品持久化事务使用 `READ COMMITTED`，仍保留父 revision 锁、匹配当前读和唯一约束。提交或回滚并归还连接后恢复默认隔离级别，政府事务不变，不修改全局设置。

该设备写事务要求 `binlog_format` 为 `ROW` 或 `MIXED`；若目标为 `STATEMENT`，应先停止设备写入并确认环境方案，不得擅改服务器。2026-09-11 公司只读检查确认 MySQL `5.7.36-log`，全局与当前检查会话的 `binlog_format=ROW`、`tx_isolation=REPEATABLE-READ`；这不是将全局隔离级别改为 RC。并发回归与真实补采结果见[阶段 M 记录](V2_PHASE_M_ACCEPTANCE_REPORT.md)。

## 3. 字符集与时间

- 字符集固定为 `utf8mb4`；
- 兼容排序规则使用 `utf8mb4_general_ci`；
- 业务和审计时间统一按 UTC 写入 `DATETIME(3)`；
- 不依赖服务器 `SYSTEM` 时区；每个物理连接都显式设置 UTC。

## 5. 公司环境上线顺序

以下为空库首次部署顺序。已有 `device_price` 的增量部署不得清库，应先备份并确认当前迁移版本，暂停采集写入后再升级；不能照此重复执行首次建库或测试清理。

1. 确认 `device_price` 是空库；
2. 在隔离 MySQL 5.7.36 完成完整测试；
3. 通过内存注入凭据运行 `alembic upgrade head`；
4. 核对表、`alembic_version` 和触发器：完整历史链 head 为 23 张业务表/40 个 MySQL 5.7 校验触发器，其中当前业务仅使用 13 张 V2 表；
5. 按来源运行 `db seed-v2-government` 或 `db seed-devices`，默认禁用，不启动采集；
6. 执行 `device-price db check` 和只读 `device-price db audit`，确认 V2 结构、UTC、兼容模式与一致性；
7. 真实采集仍须显式启用来源并满足访问门禁，再通过 `catalog smoke/crawl` 验证；不得恢复已删除的 V1 写库入口。

阶段 M 于 2026-09-11 按已有库流程完成获准备份、本地恢复和迁移演练后，将公司 `device_price` 从 `96524222b3ec` 增量升级至 `b72c910e4f31`，未清库。23 张业务表既有行与 DDL、其余 36 个触发器和其他 schema 的 11 类结构元数据未变；更换的 4 个触发器保留原有 SQL_MODE、definer 和字符集属性。后续迁移仍须检查并发状态及触发器会话属性，不得通过 `SET GLOBAL` 修改实例环境。设备正式采集与最终验收结果见[阶段 M 记录](V2_PHASE_M_ACCEPTANCE_REPORT.md)。

暂用 root 只是一项部署决策，不改变“不落盘、不提交、不记录密码”的密钥规则。后续具备条件时仍应切换到仅授权 `device_price.*` 的账号。
