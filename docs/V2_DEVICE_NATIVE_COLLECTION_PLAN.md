# V2 设备原生采集接入：现状分析与改造计划

> 状态：2026-09-11 审核修订确认；阶段 I～K 已完成，L～M 待实施
> 基线：2026-09-10 仓库代码、测试和最近一次真实采集验收记录
> 目标：五品牌从官方来源直接采入 V2；不读取、搬运或迁移 V1 业务数据
> 数据库：保留 13 张 V2 业务表与现有物理前缀，兼容 MySQL 5.7.36 / 8.x

## 1. 目标与完成定义

本轮不是“把 V1 表的数据换个地方存”，而是让 V2 原生承担电子设备的发现、抓取、解析、规格归一、价格校验、标准商品建档、持久化、重采和证据追溯。政府生鲜来源继续使用同一套 V2 存储能力。

完成后必须满足：

1. Apple、华为、小米、OPPO、vivo 的手机、平板、笔记本、台式电脑和手表，沿现有官方来源规则直接进入 V2。
2. 新设备采集不查询 V1 品牌、分类、SKU、价格或批次，也不双写 V1/V2；V1 表不存在或不可访问时仍能工作。
3. 不仅写 `source_listing` 和价格，还要建立 `brand → catalog_item → item_variant` 及可信的 `listing_match`，覆盖 V1 产品、SKU 和报价的关联查询能力。
4. 单商品失败隔离、原价语义、异常价格复核、缺失确认、幂等、乱序保护和重放不退化。
5. 正式入口只有一套 V2 业务链路；替代完成后删除旧写库流程，不长期保留转换包装层。

“覆盖 V1”指覆盖已有有效采集能力，不代表新增官网全型号发现、定制组合或未解决的 Apple Watch 总价解析。继续按 demo 交付，不增加 Redis、消息队列、查询 API、常驻监控平台或新数据源。

## 2. 改造前基线（2026-09-10）

### 2.1 两套运行链路仍然分离

| 环节 | V1 设备现状 | V2 现状与缺口 |
| --- | --- | --- |
| 实际来源 | 五品牌 adapter 均可运行 | 生产注册表仅有商务部、上海两个数据集连接器 |
| 入口 | `crawl/smoke --brand`、`build_runtime` | `catalog crawl/smoke --channel`、`build_catalog_runtime`；请求范围只识别两个政府渠道 |
| 抓取粒度 | 发现产品，获取详情，一次解析多个 SKU | 商品页接口假设发现时已有 listing；数据集接口支持一份文档多行，但不是产品目录遍历 |
| 规格规则 | 品牌解析器输出 `NormalizedProduct/Sku/Offer` | 只有生鲜品类规则，没有设备标准型号/规格规则 |
| 持久化 | 产品、SKU、offer、当前价和区间历史 | 点时观察、当前指针和来源版本可用；标准商品 Repository 已有方法，但采集流水线未调用 |
| 稳定性保护 | 价格突变复抓、产品缺失确认、发现数量保护、过期批次处理 | 已有来源锁和点时事务；这些设备运行保护尚未接入 |
| 工具 | `replay`、`db audit`、scheduler 均绑定 V1 | 缺通用 V2 重放命令和 V2 数据审计；现有政府 smoke 主要验证解析，未完整复用入库前质量校验 |
| 数据库检查 | — | `db check` 仍要求 V1 10 表与 V2 13 表同时存在 |

## 3. 路线选择

阶段 K 已完成：五品牌统一原生 V2；价格突变按整产品复抓，完整范围缺失累计及详情确认、SKU 遗漏降级、过期设备批次恢复均已接入。旧品牌采集、旧 replay/scheduler 的 CLI 执行路径已删除，完整 V2 工具与通用 V1 业务清理留在 L。实际边界及验证见[阶段 K 报告](V2_PHASE_K_BUILD_REPORT.md)。第 2 节保留改造前和各阶段的历史状态，不代表当前仍能执行旧四品牌入口。

| 路线 | 工作量与问题 | 结论 |
| --- | --- | --- |
| 包装旧 adapter，再把 V1 DTO 转成 V2 DTO | 初期快，但保留两套领域对象、校验和运行依赖，后续容易继续走旧库 | 不作为最终方案 |
| 原生改造现有五品牌 adapter，共用 V2 行处理与事务 | 保留已验证的站点逻辑，集中补齐产品多 SKU、标准建档和保护机制 | 推荐 |
| 重写爬虫并重建全套数据库 | 重复解决已经验证的抓取问题，风险和验收成本最高 | 不采用 |

复用的是发现规则、公开接口调用、页面解析、浏览器规格遍历和金额解析函数；替换的是 V1 输出契约、业务编排与持久化依赖。不为每个品牌复制 V2 流水线，也不让 V2 连接器内部长期调用 `BrandAdapter.normalize()` 再转换旧 DTO。

## 4. 目标链路与抓取粒度

```text
统一 V2 命令 / 可选的现有简单调度
  ├─ 五品牌：发现产品 → 抓取产品证据 → 解析多个 SKU
  └─ 政府：发现文档 → 下载共享证据 → 解析多个价格行
                       ↓
             共用行准备、品类规则、价格门禁
                       ↓
       设备标准建档/精确匹配（政府行无需强制建档）
                       ↓
          共用 V2 Repository 与事务 → 13 张表
```

将目前只在 fixture 中使用的单 listing 商品页契约改为产品级契约：发现结果描述产品 ID、详情 URL、分类和来源上下文，解析结果包含产品身份以及多条 SKU 来源行。单 SKU 商品就是长度为 1 的结果，不保留旧接口别名。

政府数据集契约继续存在，两者共享行 DTO、规范化和写库实现。将现有两段重复的 V2 行准备/入库代码合并，不再增加第三份复制实现。品牌/站点判断留在连接器，持久化层不出现 Apple、华为等分支。

关键粒度：

- 每个产品是一个逻辑抓取单元，一个产品的全部 SKU 使用同一组证据；不能把 1,114 个 SKU 变成 1,114 次完整产品页遍历。
- OPPO、vivo 本来就可能为每个 SKU 请求详情；保留这类必要请求，不宣称“一产品只需一次 HTTP”。
- 每个产品独立事务；另一个产品失败不影响已提交产品。身份冲突、重复规格或不完整解析导致本产品不推进可信价格。
- 政府仍按单份数据集提交；商务部各品种继续分批，不能因为接设备而变成全来源大事务。
- 产品共享的 `crawl_record.source_listing_id` 可为空，多条观察直接引用同一证据；记录的产品 ID 必须与每条 listing 的 `external_product_id` 一致。
- 批次数量明确区分发现产品数、逻辑抓取数和接受的 SKU 观察数；复抓请求数与价格条数不能混算。

## 5. 设备在 13 张表中的映射

下表省略统一的 `v2_` 前缀。

| V1 能力/来源对象 | V2 目标 | 规则 |
| --- | --- | --- |
| 品牌 | `brand` | 直接初始化五品牌，不读 V1 brand |
| 分类 | `category` | 增加设备根、电脑父类及 PHONE/TABLET/LAPTOP/DESKTOP/WATCH 叶子；不修改生鲜分类 |
| 官方商城 | `source_channel` | `OFFICIAL_MALL / SELF_OPERATED`，保留五个现有渠道代码、域名白名单 |
| 官方直营卖家 | `merchant` | 每渠道明确的品牌官方卖家，`BRAND_OFFICIAL / VERIFIED`；不将任意店铺视为官方 |
| 产品/配置族 | `catalog_item` | `item_type=MODEL`，保存品牌、系列、型号和来源可证明的公共属性 |
| 具体配置 | `item_variant` | 保留颜色、容量、内存、网络、尺寸、版本及完整必要规格；不能只存产品标题 |
| SKU 官方报价入口 | `source_listing` | 每个官方 SKU/稳定规格一个 listing；保存产品 ID、SKU ID、准确来源 URL |
| 来源 SKU 身份快照 | `listing_revision` | 只有影响配置身份的内容变化才建新版本，单纯变价不建版本 |
| 来源规格与标准规格关联 | `listing_match` | 官方精确身份规则建立可信匹配；不引入模糊匹配或机器学习 |
| 价格/状态历史 | `price_observation` | 使用 V2 点时事实，不重建 V1 `valid_from/valid_to` 区间表 |
| 当前可信记录 | `price_current` | 同 listing、版本、地区的最新可信观察指针 |
| 批次和证据 | `crawl_run / crawl_record` | 来源、产品、请求、时点、质量结果和证据可追溯 |

### 5.1 稳定身份规则

1. 型号标准键按品牌、官方来源和产品 ID 构造，不按容易变化的营销标题合并产品。保留当前配置族边界，不做跨平台去重。
2. 官方 SKU ID 优先作为来源身份；小米目前没有可靠 SKU ID，继续以产品 ID 与确定性的完整规格组合标识，不能伪造官方编号。
3. 标准 variant 键结合可证明的配置身份；规格真正变化时建立新 variant/revision，保留旧事实，不能用相同外部 SKU ID 覆盖旧配置。
4. 复用已有身份指纹和唯一键机制，不增加新哈希链、版本注册中心或品牌专属表。Apple 的部件号和华为“版本、款式”等区分字段不能在转换中丢失。
5. 不把平台 SKU 编号自动填入 GTIN 或制造商部件号。缺少内存等公开属性时允许明确缺失，不猜测参数。
6. 相同匹配重采要复用原匹配，`effective_from` 保持首次匹配时间。现有 `create_match` 会检查该字段，不能每次传入新抓取时间而触发身份冲突。
7. 某来源下架不等于标准型号在所有来源停产；来源可用状态不能无条件把全局标准商品停用。

### 5.2 价格口径

有明确价格的设备行使用 `RETAIL_OFFER + DIRECT_UNCONDITIONAL + PACKAGE_TOTAL`；单台/件按 COUNT、数量 1 表示。使用原有全国公开挂牌价口径 `NATIONAL/CN`，不承诺每个配送地区的库存或条件优惠一致。

保持原价与售价分离；无明确原价用 `NULL/NONE`。不混入补贴、领券、会员、换新、定金、分期或起售价；明确无条件直降仍是直接售价。不叠加运费、另收税费和额外包装费，也不从官网未拆分的商品含税价反推税前价。

动态页面以采集证据时间作为观察时点；同一 SKU 后续重新抓取，即使价格不变，也形成新的点时观察。相同证据、相同观察时点的重放幂等。政府仍使用来源数据日期及原有行级修订规则，两者不能统一成“按天覆盖”。

### 5.3 必要的小型迁移：无金额的可信状态

现有 V2 的领域校验、价格策略和 MySQL 约束均要求 `ACCEPTED` 观察有 `current_price`。同时，V1 的 `confirm_product_off_shelf` 会把旧金额带入新的下架观察；如果照搬进点时库，404 证据会错误地被解释成新时点的金额证明。

推荐最小调整：不加业务表或状态系统，利用现有 `price_type` 增加明确的 `AVAILABILITY_ONLY` 取值，并同步调整领域对象、策略、CHECK 和 MySQL 5.7 触发器。

- 仅表示来源证据明确证明的下架、缺货、待售等非在售状态；未知状态或未发现链接不能据此清空报价。
- `current_price/original_price/unit_price` 均为空，原价类型为 NONE，`pricing_basis=UNKNOWN`、`fee_status=NOT_APPLICABLE`；它不是金额报价。
- 只允许已知来源、已知地区和可信商品身份；抓取异常、403、验证码、非预期跳转不能被转换为状态事实。
- ON_SALE/PRE_SALE 仍必须有直接总价。普通价格行的可信门禁保持不变，政府发布值不使用这个分支。
- 可信无价状态可推进当前指针，使已下架商品不继续呈现为现售价格；旧金额仅在历史中保留。如需查看“最后已知金额”，另查最近一条有价可信观察，并展示它自己的时间。
- 官网对下架规格仍明确展示金额时，继续保存实际价格及 OFF_SHELF 状态，不强制变成无价记录。
- 无价状态也必须通过重放、乱序、恢复在售及当前投影重建测试。

无价状态的允许集合固定为 `OFF_SHELF/OUT_OF_STOCK/COMING_SOON`，仅用于 `RETAIL_OFFER`；`unit_price_unit` 也必须为空。不得以非空原价、单位价或促销文本夹带未被本次证据证明的金额。阶段 I 已建立严格的语义和数据库约束；阶段 K 已接入确认下架、缺失累计及状态推进调用方。

此外，为产品级证据增加 `crawl_record.entity_type=PRODUCT`；已有 nullable listing 外键和 `artifact_manifest` 足以承载共享证据及重放上下文，无需增加产品证据关联表。新迁移只追加，不修改已经执行过的迁移脚本；旧政府记录保持原字段值和语义。

## 6. 必须补齐的运行保护

| 能力 | 改造要求 |
| --- | --- |
| 来源与身份校验 | 同时验证品牌、渠道、分类、直营卖家、SKU 唯一性与每条输出 URL；只限制顶层请求域名不够 |
| 价格突变 | 复用现有 30% 配置；比较同 listing/版本/地区最近的有价可信观察，立即复抓同产品，配置、金额及状态一致才推进；两份证据保留 |
| 产品缺失 | 复用 `source_listing.consecutive_misses`；仅完整范围采集可累计，达到现有次数阈值后访问详情确认；一次失败或缺失不判下架 |
| 范围保护 | 商品数骤降、空发现列表和发现异常需明确失败/降级；数量保护按产品计数，不按 SKU 数计数；受限品类、smoke 或重放不能触发全站缺失处理 |
| SKU 缺失 | 产品仍被发现但某规格未被本次遍历覆盖时，不直接宣布该 SKU 下架；优先使用官网明确 SKU 状态或独立确认 |
| 状态更新 | 不让失败记录的 listing 初始化逻辑顺便恢复 ACTIVE 或清零缺失次数；重放/乱序数据也不能回滚生命周期或 URL 等当前元数据 |
| 事务与版本 | 产品级原子提交；可信规格变化切换 revision 并使旧规格当前投影失效，历史保留；不可信解析不切换版本 |
| 锁与批次 | 沿用渠道/地区锁；补齐同范围过期 RUNNING 批次处理；异常、取消和崩溃恢复有确定终态，不操作其他来源批次 |
| 同时点与重建 | 同时点冲突不按最后插入覆盖；政府保留已验证的官方修订链，设备未确认冲突进入待复核/拒绝，不能留下第二条无修订关系的可信事实供重建任选；增量结果与 rebuild_current 必须一致 |

这些机制对当前五品牌有实际调用方，不新增调度平台。政府数据不套用设备库存下架规则或机械的 30% 变价阈值，继续保持发布值口径。

阶段 K 的保守边界：

- 缺失仅在完整默认品类、无商品筛选、非查询重采且发现与已发现产品采集全部成功时累计；后续确认失败可使最终批次 PARTIAL。证据必须非 REPLAY、全部晚于采集前已有可信状态，统一比较 UTC 毫秒时点。默认 50% 产品数下限不通过时停止本批写价。
- 缺失达默认 3 次，使用**最近可信观察对应的不可变发现上下文**复查详情，不读取初始 revision 的旧 URL 来猜测下架。404/410 必须来源于整产品入口且无重定向；Apple、小米、vivo 满足当前入口约束，华为/OPPO 的选中 SKU 地址仍不能据此判整产品下架。403、超时、登录、子 SKU 接口 404 均保留旧事实并报告未确认。
- 单个 SKU 从产品结果消失仅报告 `SKU_COVERAGE_INCOMPLETE/PARTIAL`；已解析的可信 SKU 可保存，缺失 SKU 不变，不追加全配置遍历猜测状态。明确解析出的无价状态按窄门禁保存。
- 变价复核第一次记录为待确认审计，第二次完整一致且时点更新后写入可信事实；不同规格、金额、状态或复抓失败不覆盖旧价。REPLAY 突变不联网复抓，只留待复核。
- 只恢复同渠道、地区、品类范围的过期**设备** RUNNING 批次；不对政府品种开启此新增恢复规则，避免同分类不同 commodity 被误处理。

### 6.1 批次结果与退出码（审核后确认）

- `SUCCEEDED` 表示请求范围内每个已解析的来源规格/地区都有可信报价或合法的无价状态，且没有抓取、解析、范围或身份失败；不能仅凭 `failed_count=0` 判定。
- 有可信结果，但某个产品、规格或地区失败、待复核或没有可信候选时为 `PARTIAL`；完全没有可信结果或发现为空时为 `FAILED`。可信直售价和被拒绝的会员价同时出现，不会仅因存在额外条件价而把该规格判失败。
- 幂等重采以本次验证通过的候选计数，不以新增数据库行数判断成功；同份政府报价复用已有观察仍可成功。
- `accepted_count` 统计接受的观察候选（包括合法状态），`review_count/rejected_count` 保留质量结果；`failed_count` 继续统计抓取/解析失败，不能单独代替批次质量结论。
- CLI 输出显式 `status`；仅全部请求成功时退出 `0`，`PARTIAL/FAILED` 退出 `1`，参数/门禁错误退出 `2`。smoke 同样不能把零个可信结果当作通过。
- 对全部拒绝、全部待复核、部分成功、额外条件候选及幂等重采分别增加测试。上述运行判定随产品流水线整合完成，不为计数新增业务表。

## 7. 命令、重放与旧代码退出

`db seed-devices`、五品牌的 `catalog smoke/crawl` 已实现；`catalog replay` 和统一 V2 audit 待阶段 L。旧采集、重放及 scheduler 命令直接拒绝，不再构建 V1 运行时。真实采集必须遵守门禁，阶段 I～K 未访问真实来源或公司库：

```bash
# 初始化 V2 设备品牌/分类/渠道；默认不启用真实来源
uv run device-price db seed-devices
uv run device-price db seed-devices --enable

uv run device-price catalog sources
LIVE_CRAWL_ENABLED=true uv run device-price catalog smoke --channel APPLE_CN_WEB --max-products 1
LIVE_CRAWL_ENABLED=true uv run device-price catalog crawl --channel APPLE_CN_WEB
# 以下为阶段 L 目标，当前不可作为 V2 验收命令
# uv run device-price catalog replay --record-id <V2抓取记录ID>
# uv run device-price db audit
```

- 沿用 `catalog` 作为唯一采集入口；政府现有 `--commodity` 语义保留。渠道默认范围由对应连接器/来源配置提供，不继续向 CLI 堆品牌分支。
- smoke 不连数据库，使用种子定义的来源/品类配置，但与正式采集共用解析、规格和静态价格门禁；需要旧价格的变价复核属于正式采集阶段。
- V2 replay 默认只读、不联网、不写价格；使用 V2 record 的原始时间和产品/文档上下文，能重放共享证据中的全部 SKU/价格行。重放输出不等于重新采集时点。
- 新产品记录必须保留重放所需的产品 ID、分类、品牌/来源、规格上下文和每份证据的请求 URL、时间、哈希及相对路径。不得从后来变化的 listing 当前字段重新猜测原产品。已有政府记录按已保存的来源 URL、日期与白名单恢复确定性上下文；无法恢复时明确报缺证据，不补抓、不改历史记录。
- `db audit` 转为 V2：核对当前指针、观察、版本、匹配唯一性、证据、无价状态语义和批次终态；未运行的禁用来源不误报。原始文件检查和过期信息保留为手工验收能力，不建设告警平台。
- `db check` 只要求 V2 必需表；已知 V1 历史表可存在，但缺少 V1 表不能阻止运行。
- 保留现有简单 scheduler 的能力，但仅作为显式可选入口：改为调用同一 V2 流水线，只调度显式选择且启用的设备渠道；默认不启动，不顺带调度政府来源。不允许保留仍写 V1 的 scheduler，也不增加新的调度服务。
- 删除被替代的 V1 `CrawlPipeline`、价格持久化业务、运行注册表和 V1 专用 DTO/校验调用；重放和审计改造原有实现，避免多套同功能服务并存。
- 公共抓取对象、时间工具和异常基类移出 V1 业务依赖。同步 Makefile、测试、Docker 命令示例、README、运行手册、连接器契约与项目定位说明。

V1 物理表及其数据本轮默认保留为静态 demo，不再写入；删表不是 V2 接入前置条件，需另行确认。历史 Alembic 链保留，迁移元数据如需描述旧表可在迁移侧保留，但业务运行时不能依赖它。应防止后续自动生成迁移时误删这些旧表，不增加 V1 查询兼容层。

## 9. 最小验收清单

1. 五品牌现有 fixture 按同份证据核对 SKU 身份、原价、售价和状态，不以不同时间的两次官网报价强行比较；可将旧证据提炼成脱敏测试材料，不把 V1 记录导入公司 V2。
2. 一产品多 SKU 的 fetch、证据引用和事务粒度正确；重复 SKU、不同产品混入、非法域名和身份冲突不写入可信价格。
3. 官方源出现 SKU/规格新增、相同 SKU 内容变化、仅标题变化时，item、variant、revision、match 的增量行为正确；同一标准匹配重采不报冲突。
4. 同价新时点新增观察；同证据同时间重放幂等；旧观察不覆盖新观察；多地区不串价；重建当前指针与正常增量写入一致。
5. 条件价、缺少在售价、无法拆分费用与异常大幅变化不能替换可信价格；复抓不同价必须拒绝。
6. 缺失、空发现、局部采集、网络错误、确认下架、无金额状态和重新上架均有测试；旧金额不被包装成新时点报价。
7. 当前价能联表查询到型号、具体规格、品牌、官方渠道、卖家、价格性质、原价、售价、状态、时点和证据。库存未知不得显示为有货。
8. V2-only 集成用例在没有 V1 表时运行；另设 V1 表保留但无业务写入的隔离断言。测试不能连接公司库。
9. 商务部和上海的 fixture、同日修订、行级幂等与发布时点回归通过；公司验收比较既有政府来源行的全部业务字段，而不是比较共享表总行数不变。
10. 执行 `make lint`、`make test-unit`、MySQL 5.7/8.x 集成测试、镜像构建与 CLI smoke。真实页面有门禁失败时如实记录，不绕过访问控制。
11. 批次状态、CLI 退出码与可信结果一致；零新增但幂等有效不能误报失败，全部拒绝不能误报成功。

Apple Watch 的三个既有组合页缺口单列，不作为“为了 V2 验收而放宽价格规则”的理由。源站出现新的页面变化时，单独记录新增适配工作。

## 10. 工作量与优先级判断

数据库主体已具备承载能力，主要难点是产品/SKU 粒度、标准身份与匹配、状态/价格事实区分，以及旧运行保护和工具的完整接续。不是简单换表名，但也不需要重写五个爬虫或重建数据库。

粗估一名熟悉仓库的开发者需约 8～12 个有效工作日完成 I～M；这是任务拆解估计，不是承诺。源站结构稳定、测试库和公司库可用是前提；若同时要求补齐 Apple Watch 全部组合、扩大官方型号发现范围或增加每日运行保障，应另行估时，不混入本轮。

优先顺序：先证明一个产品多 SKU 可完整写 V2，再推广五品牌，最后统一入口并证明 V1 零依赖。不要先清空现有数据库，也不要先增加通用插件框架。
