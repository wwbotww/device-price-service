## 1. 决策

V1 五品牌数据已确认只是 demo，不包含人工校正、理赔案件关联或其他不可重建事实。与重新从授权来源采集相比，开发并长期维护 V1 → V2 转换器没有业务收益，还会把 V1 的区间价格语义错误带入 V2 的点时价格模型。

因此阶段 B 不实施历史回填，改为：

1. V2 影子表从空表初始化；
2. 五品牌及新增品类均由 V2 采集链路重新产生点时事实；
3. 影子验收期间暂时保留 V1 表和旧任务用于回退；
4. 阶段 G 停止旧任务并完成备份后，再按显式表清单清理 V1 demo；
5. 不生成 V1/V2 双写、转换兼容层或伪造的历史采样点。

## 2. 为什么重采成本更低

- V1 `price_history` 保存变化区间，V2 要求每次实际采集都是独立观察；转换无法恢复不存在的采样点；
- V1 没有独立卖家、来源商品版本和标准规格匹配，回填必须猜测这些身份；
- 现有原始证据可重新由采集流程产生，V1 数据没有合规保留要求；
- 一次性转换器需要复杂对账、异常恢复和长期测试，却不会服务后续真实采集；
- 空表重采直接验证最终连接器、规则包、证据和价格门禁，验收结果更接近生产行为。

## 3. 安全边界

“允许清空 V1 demo”不等于开发阶段立即执行删除。公司环境仍按以下顺序处理：

1. 阶段 F 只读记录 V1 基线；
2. 只新增 `v2_` 表并执行影子采集；
3. 验证覆盖率、价格语义、证据和运行稳定性；
4. 阶段 G 单独审核 V1 表清单和最终改名 SQL；
5. 备份、停止 V1 写入后才执行清理；
6. SQL 必须显式限定 `device_price` 和目标表名，不使用跨 schema 操作或通配符。

本阶段没有执行 DDL、DML、清表或网络采集。

## 4. 工程处理

- 删除未完成、未接入且没有测试价值的 V1 回填实现；
- 更新开发计划，将 V1 回填和行级对账从完成标准中移除；
- 保留阶段 A 的添加式影子迁移，以便阶段 F 无损验证；
- 把长期结果明确为单一 V2 权威路径，阶段 G 完成后删除旧路径，不维护兼容层。

## 5. 下一步

阶段 C 直接围绕空 V2 表实现通用采集契约。阶段 F 的对账指标改为采集覆盖率、接受/拒绝比例、当前价一致性、证据完整性和运行失败率，而不是 V1/V2 行数相等。
